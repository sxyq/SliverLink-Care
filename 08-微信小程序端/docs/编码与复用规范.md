# 编码与复用规范

本文件用于约束 `08-微信小程序端` 的后续开发方式，确保：

1. 最大程度复用旧代码
2. 小程序实现不硬搬 H5
3. UI 与现有三端保持同一品牌语言
4. 文件职责清晰，后期不会失控

## 一、总体目标

小程序端不是一个全新独立产品，而是对现有项目的移动端重新承载。

因此必须做到：

- 复用现有业务模型
- 复用现有接口定义
- 复用现有交互流程规则
- 复用现有视觉语言
- 重写平台相关能力

## 二、允许复用的内容

### 来自 `01-扫码用户端`

- 页面字段结构
- 验证流程
- 档案查看流程
- 名牌导出流程规则
- 扫码后的信息组织层级

### 来自 `02-志愿者填写端`

- 志愿者 / 家属统一登录语义
- 老人列表与详情信息结构
- 基本信息、用药、量表、二维码管理的字段定义
- 家属与志愿者角色分流规则
- 邀请码注册规则

### 来自 `04-统一后端`

- 接口路径
- 响应结构
- 错误语义
- 权限边界
- 文件下载接口

## 三、必须重写的内容

### 路由层

不能复用：

- `react-router-dom`
- hash 路由
- 浏览器地址栏参数控制

必须改成：

- 小程序页面栈
- 分包配置
- 页面 query 参数
- 扫码 / scene / path 启动参数

### 平台 API

不能复用：

- `window`
- `document`
- `sessionStorage`
- `localStorage`
- 浏览器复制
- 浏览器下载

必须改成：

- `wx.scanCode`
- `wx.setStorageSync`
- `wx.getStorageSync`
- `wx.request`
- `wx.downloadFile`
- `wx.openDocument`

### 环境变量

不能直接复用：

- `import.meta.env`

必须改成：

- Taro / 小程序构建环境配置
- `config/` 目录集中管理

## 三点一、二维码与启动参数规则

### 当前采用的入口组合

- `H5 二维码`：通用扫码入口
- `微信小程序码`：微信专用直达入口
- `首页扫码按钮`：主动扫码入口

### 必须统一的参数语义

不论入口来自哪里，最终都应收口到统一参数模型：

- `qrToken`
- `elderId`
- `archiveNo`
- `inviteCode`
- `source`

### 推荐收口位置

- 启动阶段：`src/app/app.lifecycle.ts`
- 启动解析：`src/hooks/useAppLaunch.ts`
- 页面参数工具：`src/utils/routeParams.ts`
- 后端解析：`src/services/scan/scanAuthService.ts`

### 禁止做法

- 不同入口各自发明完全不同的字段名
- 页面里到处手写 `scene` 解码逻辑
- H5 与小程序分别维护两套不一致的二维码业务语义

## 四、UI 一致性规则

### 复用目标

必须保持一致的内容：

- 颜色体系
- 页面标题层级
- 卡片式结构
- 按钮语义层级
- 信息分区逻辑
- 图标语义
- 空态 / 加载态 / 错误态表达方式

### 不允许出现的退化

- 直接使用默认白底黑字表单，丢失品牌感
- 为了图省事把原有卡片层级改成大段无分区文本
- 原 H5 有明显视觉层次，小程序却退化为纯列表

### 推荐做法

- 先抽取页面结构，再重写小程序组件
- 先统一设计变量，再逐页落样式
- 关键页面优先保留和 H5 接近的视觉秩序

## 五、目录职责

### `src/app`

负责：

- 小程序全局配置
- 生命周期
- Provider 装配
- 全局常量

不负责：

- 具体页面业务

### `src/pages`

负责：

- 首页
- 统一登录
- 角色分流

说明：

- `pages` 放首包关键页
- 页面的公共入口尽量集中在这里

### `src/subpackages`

负责：

- 扫码业务页
- 工作台业务页

说明：

- `scan` 和 `workbench` 分包，减小首包

### `src/components`

负责：

- 通用 UI 壳
- 反馈组件
- 布局组件

禁止：

- 组件中直接访问后端接口

### `src/services`

负责：

- 接口调用
- 文件下载
- 小程序 request 封装

禁止：

- 页面直接写完整接口地址

### `src/store`

负责：

- 登录态
- 当前老人态
- 启动态

原则：

- 按领域拆 store
- 页面通过 selector 读取

### `src/utils`

负责：

- 格式化
- 存储工具
- 权限纯判断
- 参数解析

禁止：

- 把完整业务流程塞进工具函数

## 六、文件实现顺序

每个页面文件正式开发时建议按这个顺序写：

1. 文件职责注释
2. 依赖的 service / hook / store
3. 页面入参定义
4. 状态定义
5. 数据获取流程
6. 交互处理函数
7. JSX 结构
8. 导出页面组件

## 八、建议的第一批真实开发文件

建议优先填充：

1. `src/app/app.config.ts`
2. `src/app/app-entry.tsx`
3. `src/services/api/httpClient.ts`
4. `src/pages/home/index.tsx`
5. `src/pages/auth/login.tsx`
6. `src/subpackages/scan/landing/index.tsx`

因为它们决定了：

- 小程序能否启动
- 首页能否进入
- 接口是否能请求
- 扫码流能否打通
- 志愿者 / 家属统一登录能否承接
