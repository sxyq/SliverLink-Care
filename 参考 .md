## 1. 引言

### 1.1 编写目的

本文档详细描述了"VulnScan代码安全分析平台"的软件需求规格。本文档面向项目经理、开发人员、测试人员、UI设计师以及最终用户，作为系统开发、测试和验收的依据。

### 1.2 项目背景

VulnScan 是一个支持多批次分析的代码理解与安全分析平台，采用统一的用户角色，实现项目管理、任务管理、多智能体分析、报告查看与源码浏览的完整闭环。系统提供代码项目解析、架构分析、安全检测、智能对话等功能，帮助用户快速理解和分析代码项目结构，发现潜在的安全问题。

### 1.3 定义与缩写

| 术语/缩写             | 定义                                                  |
| ----------------- | --------------------------------------------------- |
| JWT               | JSON Web Token，无状态认证令牌                              |
| REST              | Representational State Transfer，表述性状态转移             |
| API               | Application Programming Interface，应用程序接口            |
| ORM               | Object Relational Mapping，对象关系映射                    |
| FastAPI           | 高性能Python Web框架                                     |
| SQLAlchemy        | Python ORM框架                                        |
| SQLite            | 轻量级嵌入式数据库（开发环境）                                     |
| PostgreSQL        | 开源关系型数据库（生产环境）                                      |
| Neo4j             | 图数据库，存储代码关系（仅在detailed\_intro模式使用）                  |
| LLM               | Large Language Model，大语言模型                          |
| Agent             | 智能体，自主执行任务的AI实体                                     |
| Orchestrator      | 编排器，协调多个智能体的执行                                      |
| FileAnalyzerAgent | 文件分析智能体，执行具体文件分析任务                                  |
| Checkpoint        | 检查点，用于断点续分析的状态快照                                    |
| AST               | Abstract Syntax Tree，抽象语法树                          |
| Analysis Mode     | 分析模式：simple\_intro/detailed\_intro/security\_report |
| Run Mode          | 运行模式：fresh（全新分析）/ resume（断点续分析）                     |
| Project Scope     | 运行批次标识，区分同一项目的不同分析运行                                |

## 2. 业务需求分析

### 2.1 业务背景

#### 2.1.1 行业现状

随着软件开发的快速发展，代码理解与安全分析需求日益突出：

- 开源组件被广泛应用于商业软件中
- 新代码库上手成本高，需要快速理解项目结构
- 代码复杂度持续增长，人工审计难以应对大规模代码分析需求
- 安全问题发现滞后，传统静态分析工具误报率高

#### 2.1.2 现有问题

| 问题类型 | 具体描述                      |
| ---- | ------------------------- |
| 效率问题 | 人工代码阅读和审计耗时长，难以快速理解大规模代码库 |
| 遗漏问题 | 人工审计容易遗漏代码结构问题或隐蔽缺陷       |
| 误报问题 | 传统静态分析工具产生大量误报            |
| 技能门槛 | 代码分析需要专业知识，新成员上手困难        |

### 2.2 业务目标

#### 2.2.1 总体目标

构建一个**简洁、高效、易用**的代码安全分析平台，实现项目管理和安全分析的一体化流程。

#### 2.2.2 具体目标

| 目标编号   | 目标描述     | 衡量指标          |
| ------ | -------- | ------------- |
| BG-001 | 提高代码分析效率 | 相比人工阅读提升5倍以上  |
| BG-002 | 简化操作流程   | 用户30分钟内完成首次分析 |
| BG-003 | 降低使用门槛   | 普通开发者可独立使用    |

#### 3.4.3 分析模式参数

**analysis\_mode**: 分析模式，可选值：

- `simple_intro`: 简单介绍模式，快速生成项目概述
- `detailed_intro`: 详细介绍模式，包含架构分析和Neo4j图谱
- `security_report`: 安全报告模式（默认），聚焦代码安全分析和潜在漏洞检测

**run\_mode**: 运行模式，可选值：

- `fresh`: 全新分析（默认）
- `resume`: 从检查点恢复分析

```mermaid
sequenceDiagram
```

```mermaid
    participant EO as EnhancedOrchestrator
```

### 8.2.17 数据迁移与接口兼容要求

1. 项目来源信息从项目主表中拆出后，接口仍需继续返回 `source_type/source_url/source_local_path/source_display_name/source_archive_name/source_root_name/source_top_level_entries/source_file_count/source_directory_count/source_available`。
2. 任务运行信息独立存放在 `task_runtime` 后，接口仍需继续返回 `analysis_mode/run_mode/run_scope/status/progress/current_step/error_message/started_at/completed_at`。
3. 智能体执行、状态、日志、统计与活动负载拆分后，前端仍通过聚合结果读取 `role/status/current_file/log_path/stats/input/output/metadata`。
4. 服务启动时必须自动检查结构版本、补齐缺失表并回填历史数据。
5. SQLite 与 PostgreSQL 均必须支持相同的聚合读取和迁移逻辑。

### 8.4 检查点存储

检查点数据以文件形式存储在 `checkpoints/` 目录下，采用 JSON 格式保存分析状态：

```json
{
  "project_id": "uuid",
  "checkpoint_key": "scope_key",
  "project_path": "/path/to/project",
  "output_dir": "/path/to/output",
  "total_files": 100,
  "completed_files": 50,
  "failed_files": 0,
  "current_stage": "analyzing",
  "pending_files": ["file1.py", "file2.py"],
  "completed_file_paths": ["file3.py"],
  "failed_file_paths": [],
  "agent_count": 4,
  "agent_status": {...},
  "agent_allocation": {...},
  "analysis_mode": "security_report",
  "run_mode": "fresh"
}
```

**说明**: 检查点机制支持断点续分析功能，当运行模式为 `resume` 时，系统会从检查点恢复分析状态，仅处理未完成和失败的文件。
